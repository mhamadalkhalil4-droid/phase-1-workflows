Workflow 2 — Edit Payment Plan
Actor: Merchant  ·  Screens: SCR-PP-002, SCR-PP-001 (edit mode), SCR-SCH
🔑 Important Concepts for Edit Mode

Effective From: Defaults to today. Merchant can change it to any date. For soft changes: the system applies the changes on this date. For hard changes: this is the target date for new mandates to take effect.

Max Amount (read-only in edit mode): The Max field is read-only. It can only go up — never down. If the updated payment table requires a lower max than what is saved, the saved max stays unchanged. If the table requires a higher max, the field updates automatically. This protects the integrity of approved mandate terms.

Soft vs Hard changes: The system automatically classifies every change the merchant makes. See the table below.

Change MadeTypeWhy — and what happens
Plan name SOFT Metadata only. No financial terms change. Applied internally on the Effective From date. No bank involvement.
Collection day SOFT Timing change only. Does not affect the amounts the bank has approved. Applied internally.
Amount change that stays within the existing Max SOFT The mandate already covers this amount range. The bank has already approved this ceiling. Applied internally.
Adding or removing a payment row — Min and Max stay the same SOFT The financial bounds do not change. The bank-approved limits are still valid. Applied internally.
Frequency change HARD Changes the fundamental collection structure of the mandate. The bank must approve the new terms. New mandates required.
Lifetime change HARD Changes the duration of the mandate. Bank must approve. New mandates required.
Amount change that causes Max to increase HARD The bank-approved ceiling is no longer sufficient. A higher limit must be approved. New mandates required.
Adding or removing a row that changes Min or Max HARD The financial bounds change. The bank must re-approve the new limits. New mandates required.

Workflow 3 — Pre-Submission Missed Collections Planning
Actor: System (fully automated)  ·  Triggered by: Workflow 2, after merchant confirms applying hard changes to existing mandates  ·  Runs entirely BEFORE new mandates are submitted to the bank
🔑 Why this workflow exists — and why it runs before submission

When new mandates are submitted to the bank and old ones are cancelled or transitioning, there is always a gap or a difference. Collections that should have happened during this gap are called Missed Collections. Since we cannot change a mandate after it has been submitted and approved by the bank, everything must be planned and embedded into the new mandate's payment schedule before the mandate is submitted.

The 2-day assumption: The system assumes the bank will take 2 days to approve the new mandate. All planning is based on this window. Collections expected to fall within those 2 days are calculated and baked into the new mandate schedule before submission, so the bank approves a mandate that already includes the recovery amounts.

Missed Collections (Cancel and Reissue approach): When old mandates are cancelled immediately, there is a window where no mandate is actively collecting. The collections that should have been made during this window are the Missed Collections. They are added to the new mandate's payment schedule before submission.

Differences (Issue New First approach): Old mandates keep running while new ones go to the bank. If the new plan has higher amounts than the old plan, the payer is only being charged the old (lower) amount during the transition. The difference between the old amount and the new amount — for each collection that happened during the transition — is calculated and embedded into the new mandate schedule before submission.

Recovery Flow: If the bank takes longer than 2 days, additional missed collections beyond the planned window exist. These are handled by Workflow 4.

How amounts are placed — non-daily frequencies: Missed collections and differences are added as one-time payment entries on upcoming collection dates. If the mandate's frequency is too infrequent (dates too far apart or Max would be exceeded), the system permanently increases the frequency — e.g. Quarterly becomes Monthly — to create more collection opportunities. The plan frequency is also updated. For daily mandates, amounts are added as add-ons on upcoming recurring daily payment dates.

Workflow 4 — Recovery Flow
Actor: System (fully automated)  ·  Triggered by: Bank approval arriving after the 2-day planned window  ·  Applies only to new mandates flagged as replacing existing payers
🔑 What triggers this and what it solves

In Workflow 3, the system planned for a 2-day approval window and embedded those Missed Collections into the new mandate schedule before submission. If the bank takes 11, 14, or 20 days instead, there are additional collections that fell in the extra days that were not part of the original plan. The Recovery Flow handles these extras automatically when the actual approval date is received.

How recovery works: For non-daily mandates, recovery amounts are added as one-time payment entries on upcoming collection dates — if the frequency is sufficient to absorb them without exceeding Max. If the frequency is too infrequent (dates are too far apart or Max would be exceeded), the system permanently increases the mandate frequency to create more collection opportunities (e.g. Quarterly becomes Monthly). The plan frequency is also updated. For daily mandates, recovery amounts are added as add-ons on upcoming recurring daily payment dates. In all cases, amounts are split into installments that each fit within the mandate Max. There is no cap on the number of installments — the system keeps splitting until all recovery amounts are fully covered. These changes apply only to mandates flagged as replacing existing payers. New customer mandates are never affected.
